# Media validation bench (#342)

One scenario set that answers two different questions about a server image, and
never confuses them:

| level | question | evidence |
|---|---|---|
| `ffmpeg` | Can the FFmpeg runtime **in this image**, with its drivers, do X? | the image's own ffmpeg ran a command; the output probes as expected |
| `playback` | Did **Tesserafin** actually serve X to a client? | a real server started from the image served HLS bytes for a real library item over its API; the bytes probe as expected; the server's own log names the encoder and filters it used |

An `ffmpeg` pass is necessary, never sufficient. Only `playback` rows count as a
successful playback.

## Running it

```bash
# any image built from this tree (docker/f0-runtime-context.sh + docker build)
ci/media-bench/bench.py --image tesserafin-local:dev --out ./bench-out

# software only (no GPU on this machine, or to prove the CPU path)
ci/media-bench/bench.py --image tesserafin-local:dev --no-device

# fixtures from another image (they are validated either way: the HDR10 one must
# really be 10-bit PQ/BT.2020, which a single-depth libx265 cannot write)
ci/media-bench/bench.py --image IMG --fixture-image OTHER_IMG

# a subset of the playback scenarios
ci/media-bench/bench.py --image IMG --skip-ffmpeg-level --only sdr,hdr,recovery
```

Requirements on the machine running the script: `python3` (stdlib only) and a
`docker` CLI. Nothing else: no host ffmpeg, no published port, no bind mount.

Outputs in `--out`: `results.jsonl` (one JSON object per scenario, with the
evidence), `summary.md` (table), `server.log` (the last server container's log).
Exit code 0 = every scenario that ran passed, 1 = a failure, 2 = could not start.

## Provider independence

Every action is a `docker` CLI call. Fixtures are generated by the image's own
ffmpeg into named volumes; HTTP is spoken from inside the server container with
the image's own `curl`; results come back over `docker exec`. The bench therefore
runs unchanged against **any Docker endpoint**:

```bash
DOCKER_HOST=ssh://bench@gpu-host.example ci/media-bench/bench.py --image ghcr.io/...@sha256:...
```

A cloud adapter has exactly one job: provision a host with Docker and a render
node, make the image pullable there, and export `DOCKER_HOST`. It does not touch
the scenarios. No adapter is shipped yet (deliberately: no multi-provider
campaign in this iteration).

## Scenarios

`env` (recorded, not graded as playback):

- `identity` — image id, licence/revision labels, the ffmpeg the image's CMD
  passes with `--ffmpeg`, SHA-256 of `ffmpeg`/`ffprobe`, the F0 archive line from
  `/opt/tesserafin-ffmpeg/ARCHIVE.sha256`, a hash of `-buildconf`, whether
  `libfdk` appears in it, kernel, `DOCKER_HOST`.
- `gpu` — render node, PCI vendor:device and kernel driver read from the Docker
  host's `/sys`, the node's group id.
- `fixtures` — four generated files and their digests: SDR (MPEG-2, 180 s, so it
  can never be direct-played and a seek lands outside the first job), HDR10
  (HEVC Main10, PQ/BT.2020 with mastering metadata), ASS and PGS (a solid white
  box at a known place over a dark picture; `gen-pgs.py` writes the PGS stream,
  since FFmpeg has no PGS encoder).

`ffmpeg`:

- `software-h264`, `x265-main10` (software HEVC 10-bit encode, with the x265
  build's bit depth), `vaapi-h264` (names the VA driver it loaded),
  `vulkan-device` (names the Vulkan device), `libplacebo-hdr10-sdr` (output must
  be tagged BT.709), `burn-ass`, `burn-pgs` (the box region's mean luma).

`playback` (a real server; hardware type left to the server's own startup
decision; tone-mapping enabled):

- `startup` — seconds to a stable `/health` 200 and the logged
  `Hardware acceleration decision` (`Mode=hardware` expected with a device).
- `hls-ts-sdr`, `hls-fmp4-sdr` — master → main → segments, the way a client
  plays; time to first segment; H.264 out; the encoder the server used (a
  hardware one when a device is given, never one without).
- `seek` — segment 20 requested directly: the server must restart ffmpeg with
  `-ss` equal to that segment's playlist offset, and the bytes must carry it.
- `hdr10-to-sdr` — SDR out, a tone-mapping filter in the server's command and,
  with a device, the Vulkan `libplacebo` path specifically.
- `burn-ass`, `burn-pgs` — `SubtitleMethod=Encode`; the box is measured in the
  served bytes.
- `concurrency` — N (default 3) sessions at once, all served.
- `stop` — `DELETE /Videos/ActiveEncodings` leaves no ffmpeg process.
- `fallback-device-removed` — same persisted GPU-era state, container restarted
  without the device: `Mode=software` and a software encode is served.
- `recovery-midstream-hw-fault` — hardware → software **during** a playback:
  `drmfault/drmfault.c` (built against the image's own glibc in a throwaway
  container) is preloaded into the server's ffmpeg; after three hardware
  segments the next AMDGPU command submission fails with `ECANCELED`. Passes only
  if the driver reported the lost context, the next segment request is answered
  `410` with `X-Tesserafin-Playback-Recovery: software`, the client's reload is
  served by a software encoder, and a later playback is software from the start
  (docs/hardware-transcode-recovery.md). AMD only; skipped, with the reason, on
  another GPU vendor.

## What it does not prove

- Only VAAPI on AMD (radeonsi/RADV) has been run. Intel (iHD/QSV), NVIDIA, ARM
  SoCs: not run; nothing here claims them.
- Image quality is not measured (no SSIM/ΔE): HDR → SDR is checked by tagging,
  filter path and pixel format, not by a colour-accuracy threshold (#340 keeps
  that question open).
- The native packages (.deb/.rpm/.tar.gz) are not driven yet: the bench needs a
  server it can start through Docker. A native target is one more executor
  (`start_server`/`http`/`logs`), not new scenarios.
- No browser is involved: "playback" means the server served valid, decodable
  HLS for the request a client makes. The web player's own recovery UI is
  covered by the browser suites, not here.
